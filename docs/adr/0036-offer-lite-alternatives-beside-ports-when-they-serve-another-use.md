# Offer lite alternatives beside ports when they serve another use

## Context and Problem Statement

ADR 0028 offers lite alternatives for components without a port. The `tabs`
port follows the ARIA tabs pattern: its panels are in one page, and the tabs
script switches them. Hono apps are often multi-page, where each tab is a URL
(settings pages, a repository's tabs, `?tab=`) and the server renders only the
current one. The port cannot serve that: its triggers are buttons (upstream's
TabsTrigger takes no `render` here), and a link with `role="tab"` would
promise tab behavior for page navigation. How should a script-free variant of
a ported component be offered for such a use?

## Decision Drivers

* Correct semantics for the use: navigation links with `aria-current`.
* No JavaScript.
* Upstream's look in every style, following upstream changes.
* The port's name, API and DOM stay as upstream's.
* Installing one of them does not bring the other's files or script.

## Considered Options

* A lite alternative beside the port (`tabs-lite`)
* A link mode in the port (`TabsTrigger href`)
* A documented recipe with copied classes
* A derivative generated from the port by transform rules

## Decision Outcome

Chosen option: "A lite alternative beside the port", because it gives the use
its own semantics while the port stays a translation of upstream. A lite
alternative may exist beside a port when it serves a use the port does not.
It keeps the `-lite` suffix and everything else of ADR 0028 (a hand-written
source in `lite/`, class recipes per style, `basedOn` review), and in
addition it does not import the port and uses its own `data-slot` values, so
the port's client script never acts on it. Its notes say which use each one
serves.

`tabs-lite` renders a `<nav>` of links. The trigger whose `value` matches the
root's gets `aria-current="page"` and `data-active`, the attribute upstream's
classes style, so the classes of upstream's Tabs, TabsList and TabsTrigger
apply unchanged; the recipe stops generation when upstream selects on a state
the lite parts do not render.

### Consequences

* Good, because multi-page apps get tabs that are links, with no script, in
  upstream's look.
* Good, because the port is unchanged and the two can be installed together.
* Bad, because `-lite` now also means "a script-free variant for another
  use", not only "until a port exists".
* Bad, because such an alternative is designed here, like those of ADR 0028.

### Confirmation

`generator/tests/lite.test.ts` covers the recipe's checks,
`generator/tests/catalog/build.test.ts` that `tabs-lite` installs neither the
port nor a script, `tests/render/tabs-lite.test.tsx` the DOM, and
`tests/visual/lite.spec.ts` compares it with upstream's Tabs and checks that
it is a navigation of links.

## Pros and Cons of the Options

### A link mode in the port

* Good, because there is one component.
* Bad, because it changes the port's DOM and API beyond upstream (ADR 0007)
  and mixes two ARIA patterns in one component, with exceptions in the tabs
  script.

### A documented recipe with copied classes

* Bad, because copied classes do not follow the style or upstream changes.

### A derivative generated by transform rules

* Bad, because the rules would depend on upstream's classes and structure,
  which translation rules must not.
